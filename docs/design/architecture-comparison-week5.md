# Week 5 Architecture-to-Implementation Comparison

## Purpose and comparison baseline

This document compares the five-component Week 3 design in `docs/architecture.md`, `docs/design/design-decisions.md`, and `docs/design/component-interfaces.md` with the implementation currently present in `src/rdq/`. It records implemented behavior and material differences; it does not claim that the prototype has been validated for production use or that its synthetic behavior represents any specific retailer.

## Component comparison

| Component | Week 3 design | Implemented in Week 5 | Differences, rationale, and current boundary |
|---|---|---|---|
| 1. Synthetic world generator | Seeded stores, products, warehouse, historical sales, and separate hidden future true demand. | `generate_world(WorldConfig)` creates all five in-memory DataFrames, with deterministic rows from the seed. The CLI prints counts and samples but withholds true-demand samples. | The generator matches the principal contract. Warehouse data is one opening snapshot at the end of the historical period, not a dated replenishment stream. Historical sales are generated directly from demand and do not simulate historical inventory constraints. The generated future truth exists in the pipeline result for evaluation/simulation; it is not passed to the forecaster. |
| 2. Pluggable forecaster | A `Forecaster` protocol with `fit(sales_history)` and `predict(horizon)`, error-injection emulator, and optional real model. | `Forecaster` protocol and `ErrorInjectionEmulator` implement `fit` and `predict`. The emulator uses each store-product pair's trailing history baseline and configurable bias, seasonal drift, variance, and seed. | The protocol and core emulator are implemented. No statistical or ML model plug-in is implemented. The emulator's noise parameter is used as a variance (noise standard deviation is `sqrt(variance) × baseline`). The Week 3 prose sometimes showed `predict(history, horizon)`; the concrete interface specification's `fit`/`predict` contract is the one used in code. |
| 3. Replenishment simulator | Apply minimum-stock, pack-size, and warehouse constraints; produce separate decision and outcome tables with inventory and sales indicators. | `simulate_replenishment` applies a minimum target, store inventory carry-over, pack-size rounding, and a finite warehouse stock allocation per product and day. It returns one combined DataFrame with requested/order/shipped quantities, stock balances, sales, lost sales, overstock, stock-out, and a cause label. | Decisions and outcomes are combined into a single row set rather than separate tables, avoiding duplicated keys and simplifying the shared pipeline/dashboard interface. Warehouse stock is depleted across the horizon, but no replenishment inflow or dated warehouse receipts are modeled. Pack-constrained allocations are shared proportionally across stores with deterministic largest-remainder allocation, an explicit simulation simplification. |
| 4. Evaluation framework | Compare forecasts to true demand, decisions to shipments/outcomes, calculate WAPE/MAPE/bias by segments, and classify deviations; validate known injected causes. | `evaluate_results` calculates WAPE, MAPE, and bias overall and by store, category, season, and store-product. It summarizes observation and lost-sales shares by the simulator's `deviation_cause`. | Cause labels are currently assigned in the simulator using a fixed priority (stock constraint → rule constraint → model error → other), not independently inferred by the evaluator. The heuristic checks whether shipped quantity was below pack-limited orders, whether minimum-stock or pack-size rules restricted the requested order, and whether forecast differed from true demand. These are mutually prioritized labels, not proof that one factor exclusively caused the lost sales. Hand-calculated metric tests exist; dedicated known-answer tests demonstrating recovery of each injected cause and overlapping-cause behavior remain for later validation. |
| 5. Dashboard | Streamlit UI with store/category/date filtering and performance drill-downs. | `dashboard.py` runs the shared pipeline, supports synthetic run configuration and store/category/date filters, and displays metrics, cause summary, forecast-vs-demand chart, segment metrics, and simulation rows. | The dashboard is a separately launched Streamlit entry point, not launched automatically by the CLI pipeline. It recomputes filtered metric summaries from filtered simulation records. The current view provides core inspection but not every planned view, such as explicit best/worst performer rankings. |

## Pipeline and interface differences

- The documented Week 3 command `python -m rdq.pipeline --seed 42` is not the implemented CLI. The current command is `.venv\Scripts\python -m src.rdq --seed 42`; the shared orchestration function is `run_pipeline(PipelineConfig)` in `src/rdq/pipeline.py`.
- The pipeline runs generation → fit/predict → simulation → evaluation in memory. `true_demand` is available to the simulator and evaluator but is absent from the forecaster inputs. There is no database, external API, or real-data file in this run path.
- `PipelineResult` returns the generated world, forecasts, combined simulation outcomes, and evaluation result. This differs from the Week 3 conceptual diagram's separate decisions/outcomes/metrics tables.
- The dashboard command is `.venv\Scripts\python -m streamlit run src\rdq\dashboard.py --server.address 127.0.0.1 --server.port 8501 --server.headless true`.

## Evidence collected for this comparison

The following are actual outputs from the local Python 3.12 environment, recorded under `evidence/week-05/`:

1. `pipeline-run.txt` — default 10-store, 200-product run with seed 42. It produced 10 stores, 200 products, 200 warehouse rows, 730,000 historical rows, 56,000 future-demand rows, 56,000 forecasts, and 56,000 simulation rows. The CLI withheld future-demand samples. The overall synthetic-run metrics were WAPE 0.5973, MAPE 0.5137, and bias 0.0711. These values describe this generated run only; they are not real-retailer performance estimates.
2. `pipeline-run-repeat.txt` and `repeatability-check.txt` — a second run with the same seed and settings; Windows `fc /b` reported no differences between the complete CLI outputs.
3. `tests.txt` — `python -m unittest discover -s tests -v` ran 27 tests and finished with `OK`. Coverage includes generator validation/reproducibility, emulator behavior, simulator constraints, hand-calculated metric checks, end-to-end repeatability, and a dashboard smoke/filter test. This is not the Week 6 comprehensive validation or known-answer cause-classification proof.

## Conclusion and remaining design work

The Week 3 five-component architecture is substantially represented by working modules and a runnable pipeline. The main intentional implementation adjustment is combining decisions and outcomes into a single simulation table and sharing one orchestration path between CLI and dashboard. Important gaps are the optional ML forecaster, separate decision/outcome artifacts, fuller warehouse replenishment dynamics, and controlled known-answer cause-classification validation. The cause labels and synthetic metrics must therefore be treated as prototype diagnostics under stated rules, not as a proven general attribution method.
